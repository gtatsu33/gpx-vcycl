# tools/ — 物理モデル(CdA/Crr)キャリブレーション用スクリプト群

`src/domain/physics.js` の `DEFAULT_PHYSICS`(CdA・Crr)を実走データから検証・
推定するために作ったスタンドアロン解析スクリプト。**アプリ本体には組み込まれておらず、
ビルド・実行時には一切使われない。** Python(numpy/scipy)とNode.jsの2系統がある。

対象GPXはStravaエクスポート形式(`<power>`拡張タグを含むもの)を想定。

## 実行環境

- Python: `numpy`, `scipy` が必要（`python -c "import numpy, scipy"` で確認）
- Node: プロジェクトの `node_modules`（`jsdom` を含む）がインストール済みであること
- Windowsのコンソールで日本語出力が文字化けする場合は `PYTHONIOENCODING=utf-8` を付けて実行する

## スクリプト一覧

### route_distance_check_real.mjs（★最有力・まず使うべきもの）

アプリ本体の `Route` / `RideSimulator` クラスを **そのままimportして** 使い、
実走GPXの実測パワーを時系列で流し込んでシミュレーションし、アプリが計算する
走行距離と実測(GPS)走行距離を比較する。標高平滑化(300mウィンドウ)・勾配計算
(50mバケット)を含め、自前の再実装を一切使わない＝最もアプリの実挙動に忠実。

```
node tools/route_distance_check_real.mjs <GPXファイルパス> [--mass 80] [--cda 0.32] [--crr 0.005]
```

出力: 実測距離・アプリ計算距離・誤差(m, %)。コース終端に到達したらそこで打ち切り
（＝実測より短い時間でコースを完走した＝アプリの方が速く進みすぎている、という意味）。

### route_distance_check.mjs（非推奨・参考用）

上と同じ目的だが、標高平滑化を独自実装（時間ベース移動平均）していたため、
アプリ実際の地形処理（距離ベース300m回帰＋50mバケット）と一致しない。
検証の結果、この違いだけで結果の符号すら反転するほど大きくズレることが判明した
（詳細は下記「分かったこと」参照）。**キャリブレーション目的では
`route_distance_check_real.mjs` を使うこと。** `--real-position` フラグで
位置フィードバックを切った診断用モードも持つが、これもアプリの実挙動とは別物。

### find_steady_segments.py

実走GPXから「定常走行区間」（パワーの変動係数が小さい・勾配が小さい・一定時間
継続）をスライディングウィンドウで自動抽出し、区間ごとの平均速度・平均パワー・
平均勾配から、微分を使わない線形最小二乗でCdA/Crrを分離推定する（Chung法の
定常区間バージョン）。

```
python tools/find_steady_segments.py <GPXパス> [--window 180] [--max-grade 1.5] [--max-power-cv 0.15] [--mass 80]
```

条件を満たす区間が少ない実走データ（信号や坂の多いコース等）では2〜3点しか
取れず、統計的信頼性が低くなる点に注意。無風・平地・複数速度域のデータほど
向いている。

### calibrate_physics.py（Chung法・仮想標高フィット）

パワー・速度・標高をライド全体で使い、物理式を積分した「仮想標高」が実測標高に
最も一致するようCdA・Crrを2変数最適化する。長時間ライド1本では気圧ドリフトや
GPSのコーナーカットによる系統誤差、およびCdA-Crrの分離不良（コスト関数が
対角線状の「谷」になる＝一意に定まらない）が起きやすく、実データでは信頼できる
結果が得られなかった（下記参照）。グリッドサーチで谷の形状を可視化する用途に
向いている。

```
python tools/calibrate_physics.py <GPXパス> [--mass 80]
```

### coast_down.py（コーストダウン法・GPS位置ベースのGPXには非推奨）

パワー=0の惰性走行区間だけを使い、Savitzky-Golayフィルタで速度・加速度を
滑らかに推定して `dv/dt vs v²` の線形回帰でCdA/Crrを分離する手法。理論上は
分離性が良いはずだが、**GPSのDoppler速度（ネイティブ速度フィールド）を持たない
GPX（位置(lat/lon)だけを記録するタイプ）では、加速度＝位置の2階微分の計算が
1HzのGPSジッターに支配され、実用に耐える精度が出なかった**（決定係数R²が
0〜0.46程度、CdA/Crrが負値になるケースも多発）。GPSネイティブ速度や車輪速度
センサーのログがあるデータでのみ再挑戦する価値がある。

## 分かったこと（2026-08時点の調査サマリ）

1. **アプリは「シミュレート上の現在位置」で地形(勾配)を参照する
   （`src/domain/simulator.js` の `tick()`）。** これは実装として正しい設計だが、
   検証スクリプト側でCdA/Crrを少し変えるだけで、位置のズレ→違う地形→速度の
   ズレ、というフィードバックが積み重なり、結果が非連続に(チャオティックに)
   振れることがある。単発の長時間ライド1本の距離誤差だけを見てパラメータを
   逆算するのは危険。
2. 自前で標高平滑化ロジックを再実装すると、アプリ本来の処理（300m回帰＋50m
   バケット）とズレて、誤差の符号すら反転するほど結果が変わりうる。
   **キャリブレーションには必ずアプリの実クラスをimportして使うこと。**
3. `route_distance_check_real.mjs` で2本の実ライド（起伏のある海沿いコース／
   山岳クライム主体のコース）を検証した結果、既定値(CdA=0.32, Crr=0.005)で
   どちらも距離を「長く」計算する（アプリの方が実際より速く進む）方向の誤差が
   出た。Crr=0.0030（実タイヤの公称値）に固定してCdAを振っても、2本のライドが
   要求する最適CdAが一致せず、単一のCdA/Crrで両方をゼロ誤差にはできなかった。
   風・コース特性・体重変動などの影響を切り分けるには、無風・平地・複数速度域
   という条件の揃ったデータが必要、という結論に至った。
