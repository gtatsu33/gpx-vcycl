1. 技術スタック
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ホスティング   : Cloudflare Workers（静的アセット配信 + Workerスクリプト。
                   @cloudflare/vite-plugin 経由でVite/Workers runtimeを統合）
  フロントエンド : Vanilla JavaScript（ESモジュール、フレームワークなし）
  ビルド        : Vite 8 + @cloudflare/vite-plugin
  ストレージ     : IndexedDB（idbライブラリでラップ）
  BLE           : Web Bluetooth API（navigator.bluetooth）
  地図(2D)       : Leaflet.js（OpenStreetMapタイル）
  地図(2D、代替) : Google Maps JavaScript API + Street View
                   （オーナーモード限定、googleMapView.js）
  3Dマップ       : Three.js（WebGLRenderer、手組みのジオメトリ生成）
  外部DB(リモートGPX): Supabase JS クライアント（Storage読み取りのみ）
  サーバー処理    : Cloudflare Workers（単一Workerスクリプト src/worker/index.js。
                   Strava OAuth秘匿・オーナーモード認証・Street View中継のみ。
                   それ以外はクライアント完結）
  デプロイCLI     : wrangler 4
  テスト         : Vitest + jsdom
  CSSフレームワーク: なし（素のCSS、index.html内に直書き）

  ※ npm run build は @cloudflare/vite-plugin により2つのVite environment
    （Worker用・クライアント用）をビルドし、dist/ 以下に出力する。
    npm run deploy で vite build → wrangler deploy を実行し、
    Cloudflare Workersへ静的アセット＋Workerスクリプトを一体でアップロードする。

  ストア          keyPath        追加バージョン   内容

5-1-1. routeProgress ストア（複数日ライド用、KVキー）
────────────────────────────────────────
  キー: `${routeId}:${reversed ? 'r' : 'f'}`
  値:   { distanceM, updatedAt }

  API（storage/routes.js）:
    getRouteProgress(routeId, reversed) → { distanceM, updatedAt } | undefined
    saveRouteProgress(routeId, reversed, distanceM) → void
      ライド終了時（main.jsのhandleRideFinished）に、そのライドの最終
      到達距離（summary.samples.at(-1).distanceM）を無条件で上書き保存する。
      ブラウザのサイトデータ削除で消えても実害は「初期値が0に戻る」のみ
      （事前ライド画面の開始距離欄に手動入力すれば引き続き再開できる）。
      保存と同時に、終了したライドのrouteIdが現在選択中のselectedRouteIdと
      一致する場合、selectedStartDistanceMをlastDistanceMへ更新し、
      routePicker.jsのsyncStartDistance(lastDistanceM)（開始距離欄・
      標高プロファイルのマーカー再描画。notify:falseでonStartDistanceChanged
      は呼ばない）とmain.jsのpreviewAtDistance(lastDistanceM)（3D/2Dマップ・
      ActiveIndexTracker.seekTo/MapillaryLookahead.seekToによる先読み状態の
      再同期）を呼ぶ。これを怠ると、事前ライド画面に戻った際の開始距離表示が
      0のまま更新されず、かつselectedMapillaryLookahead/Trackerが前回ライド
      終了時点のindexに取り残されたまま次のライドへ流用され、Mapillary写真が
      新しい開始距離（0など）に追従せず前回終了時点の写真のまま固定される
      不具合があった（修正済み）。

────────────────────────────────────────
5-2. rides ストア（レコード形状）
────────────────────────────────────────
  {
    id, kind: 'route' | 'workout', routeId, routeName, startedAt, endedAt,
    totalDistanceM, totalElapsedSec,
    avgPowerW, avgCadenceRpm, avgHeartRateBpm,
    samples: [{ timestampMs, lat?, lon?, elevationM?, distanceM,
                velocityMs, gradientPercent?, powerW, cadenceRpm,
                heartRateBpm }],
    isDraft: boolean,
    uploadStatus: 'pending' | 'uploaded' | 'failed',
    uploadedAt, stravaActivityId, uploadError,
  }
  （lat/lon/elevationM/gradientPercentはルートモードのみ。ワークアウト
    記録には含まれない。isDraftは走行中の自動保存で作成され終了操作が
    まだ行われていない記録の場合true。kindは記録の種別（ride/rideKind.js
    のRIDE_KIND）で、Strava送信条件・FIT形式・登録名の振り分けは必ず
    これで行う（他フィールドからの推定はしない）。RideController／
    WorkoutControllerのstop()サマリーとgetCheckpoint()がkindを持ち、
    buildRideRecord()がassertRideKind()で検証する（未設定・不正値は
    例外）。kind導入前に保存された記録はkindを持たず、履歴からの
    アップロード等で例外になる（ブラウザ側のデータ消去で対処）。
    DBスキーマ上の新規ストア追加は
    不要（IndexedDBはフィールド単位でスキーマレス）。9-4節参照）

  API（storage/rides.js）:
    saveRide(summary) → id              集計値を計算しisDraft:falseで保存
    saveDraftRide(summary, existingId=null) → id
      走行中の定期自動保存用。buildRideRecord(summary, isDraft:true)を
      existingId指定時はput（上書き更新）、未指定時はadd（新規作成）。
      1走行につき最初のsaveDraftRide呼び出しで採番されたidを以降の
      呼び出しでexistingIdとして渡すことで、同一レコードを使い回し
      履歴に重複を作らない。
    finalizeDraftRide(id, summary) → id
      下書きレコードをisDraft:falseの確定記録に更新（put、アップロード
      状態は'pending'にリセット）。呼び出し元（main.js/rideEndModal.js/
      rideHistory.js）はfinalizeDraftRide後、必要ならuploadToStrava→
      markUploaded/Failedを続けて呼ぶ。
    listRides() → record[]              startedAt降順でソート
    getRide(id) → record
    markUploaded(rideId, stravaActivityId) → key
    markUploadFailed(rideId, errorMsg) → key
    deleteRide(id) → void                下書きの破棄にも流用する

7-3. physics.js
────────────────────────────────────────
  G_MS2 = 9.81 (m/s²)　　RHO_KGM3 = 1.225 (kg/m³)
  DEFAULT_PHYSICS = { massKg: 80, cdA: 0.32, crr: 0.005 }

  altitudeFactor(elevM) → number
    max(0, 1 - max(0, elevM-1500) * 0.0001)
    （1500m以下は1.0、以降100mごとに約1%低下）

  stepVelocity(powerW, gradientPercent, currentVelocityMs, dtSec,
    {massKg, cdA, crr}) → number（新しい速度 m/s）
    theta = atan(gradientPercent/100)
    vEff  = max(currentVelocityMs, 0.5)  // 発進時のゼロ割回避
    pRolling  = crr·massKg·G_MS2·cos(theta)·vEff
    pAir      = 0.5·RHO_KGM3·cdA·vEff³
    pGravity  = massKg·G_MS2·sin(theta)·vEff
    accel = (powerW - pRolling - pAir - pGravity) / (massKg·vEff)
    return max(0, currentVelocityMs + accel·dtSec)

7-4. torque.js
────────────────────────────────────────
  calcTorque(powerW, cadenceRpm) → number|null
    T[N·m] = P[W] × 60 / (2π × cadence[rpm])
    cadenceRpm<20 または powerW<=0 のとき null
    （近似が不安定になる領域のガード）

7-5. simulator.js
────────────────────────────────────────
  class RideSimulator（route.jsとphysics.jsの橋渡し。タイマー・BLE・
  UIには関与しない純粋シミュレーション。tickループの主導権は
  ride/rideController.jsが持つ）

    constructor(route: Route, params)
    set altitudeEffectEnabled(bool)
    tick(powerW, dtSec)
      gradient = route.getGradientAt(s.distanceM)
      elevM    = route.getElevationAt(s.distanceM) ?? 0
      factor   = altitudeEffectEnabled ? altitudeFactor(elevM) : 1
      effectivePowerW = powerW × factor   ← 高度によるパワー低下は
                                             ここで速度計算に反映される
      newV = stepVelocity(effectivePowerW, gradient, s.velocityMs,
                           dtSec, params)
      s.distanceM = min(prevDist + newV×dtSec, route.totalDistanceM)
      elevationGainM は正の標高差のみ加算
    getState() → {distanceM, velocityMs, elapsedSec, elevationGainM,
      altitudeFactor, currentLat, currentLon, currentGradientPercent,
      headingDeg}

      時計回り）で算出、残距離僅少時は0

    pause() / resume() / reset()

────────────────────────────────────────
  parseZwo(xmlText) → {name, segments}

        （IntervalsT展開分は空）。その他の未対応タグは無視
    属性読み取りはattr(el, 'Name','name')のように大小文字両対応。

  totalDurationS(segments) → 合計秒数
  ftpColor(ftpRatio) → 色コード（<0.60灰, <0.75青, <0.90緑, <1.05黄,
    <1.18橙, それ以上赤）

9-2. workoutController.js
────────────────────────────────────────
  定数: TICK_MS=100, SAMPLE_INTERVAL_MS=1000, ERG_UPDATE_MS=1000,
    ERG_THRESHOLD_W=5, AUTO_PAUSE_ZERO_CNT=10, AUTO_RESUME_HIGH_CNT=10,
    AUTO_RESUME_POWER_W=10

  locateSegment(segments, elapsedS) → {idx, t}（区間内進行率0〜1）
  calcTargetW(seg, t, ftpW) → number|null
    steady: round(powerLowFtp×ftpW)
    ramp:   線形補間 (powerLowFtp+(powerHighFtp-powerLowFtp)×t)×ftpW
    free:   Power指定あり→round(powerLowFtp×ftpW)（表示専用）、なし→null

  class WorkoutController（route/mapView/hudView非依存。距離・速度は
  勾配0固定でphysics.stepVelocityを流用した簡易参考値扱い）

  コンストラクタ: segments(必須), ftpW(必須), getLiveData(必須),
    ftmsClient=null, onStateUpdate=null, onFinished=null,
    onAutoPause=null, onAutoResume=null, smoothingWindowSec=3,
    params=null(既定DEFAULT_PHYSICS)

  start() → #ergPrepare()（FTMS reset→requestControlで前状態をクリア）
    →interval開始
  pause() → 手動一時停止。#resetErg()（FTMSへreset送信）
  resume() → #ergPrepare()再実行
  resumeFromAutoPause() → onAutoResume発火
  setFtpW(ftpW) → 実行中でも目標パワー計算に即反映
  stop() → {startedAt, endedAt, samples}|null

  #tick()（100ms毎）:
    1. dtSec上限0.5s
    2. 平滑化パワー/ケイデンス取得
    3. 停止中でなければelapsedMs加算、stepVelocity(gradient=0)で
       distanceM/velocityMs更新（参考値）
    4. 生パワーでゼロ/高パワー連続カウント更新
    5. #checkAutoPause()：自動一時停止/再開判定（5-5節ロジック）
    6. locateSegment→calcTargetWでtargetPowerW算出
    7. FTMS制御可能ならtargetPowerWをsetTargetPower（ERGモード、
       ERG_UPDATE_MS毎または変化量≥ERG_THRESHOLD_Wで即時送信）。
       FreeRide区間は目標値の有無によらず#updateErgにnullを渡し
       #resetErg()（ERG OFF）。HUD/グラフ/区間リストには目標Wを表示し、
       パワー乖離アラートはfree区間では判定しない
    7b. 区間内経過秒数>=offsetSの最新textEventをactiveMessageとし
       （無ければnull）、onStateUpdateのstateに含める
    8. onStateUpdate毎tick発火（10Hz）
    9. 非停止中のみ1Hzサンプル記録: {timestampMs, powerW, cadenceRpm,
       heartRateBpm, distanceM, velocityMs}（位置・標高・勾配は含まない）
    10. 完了判定でstop()+onFinished

  既知の実装メモ: #checkAutoPause() 内で手動一時停止からの自動解除
  判定に参照している `now` 変数のスコープが実装上わかりにくい箇所が
  ある。将来リファクタ時に要確認（動作自体は現状の手動テストで
  問題は出ていない）。

10-4. eleView.js（3Dマップ、Three.js）
────────────────────────────────────────
  class EleView(containerEl)
    コンストラクタでcontainerEl.style.position='relative'、canvas生成、
    WebGLRenderer(alpha:true, 背景透過でCSS側の空色を活かす)、
    PerspectiveCamera(fov50)、Fog(FOG_NEAR=200〜FOG_FAR=800m)、
    ResizeObserverでリサイズ追従。加えて描画ループ（毎フレーム）内でも
      コンテナの実サイズ変化を検知し次第renderer/cameraへ同期する
      （#syncedW/#syncedHで前回値と比較、変化があった場合のみ実処理）。
      コンストラクタ実行時点でコンテナが非表示タブの中にありサイズ0の
      ことがあり、その場合ResizeObserverの初回発火・main.js側の明示的
      resize()呼び出しだけでは正しいviewportに復帧しきらないケースが
      あったため、フレーム毎の追従を必須の保険としている。
    setRoute(route) → ルート点群から道路リボン・壁・センターライン・
      エッジのメッシュを再構築、1kmごとの距離看板・ウェイポイント看板
      （makeSignSprite、Canvas texture）を配置
    update(distanceM) → 看板の表示/非表示切替のみ（カメラ位置は
      内部のrequestAnimationFrameループで目標distMへLERP追従）
    previewAt(distanceM) → 開始距離の選択・変更時など、LERP追従を挟まず
      即座にその地点へカメラを飛ばす（#currentDistM/#targetDistM両方を
      即時セット）
    道路色は勾配によりroadColor()で決定（10-3節と同一しきい値）。
      buildPts3D()は道路メッシュの頂点列を作る際、GPX生ポイントの
      間隔がCOLOR_SAMPLE_M(20m、hud.jsの1km勾配プロファイルと同じ
      間隔)より粗い区間に、route.getGradientAt(distM)で色のみを
      算出した補間点を追加する（位置はx/y/z線形補間、勾配値は
      再計算）。これによりGPXの点密度に関わらず、実際にトレーナーへ
      送られる勾配（50mバケット）の境界と道路の色境界が一致する。
    ROAD_HALF_W=8.0m, Y_EXAG=2.5（標高の視覚的誇張）,
      CAM_HEIGHT=3.0m（実寸、Y_EXAGは掛けない生のワールド座標オフセット）,
      LOOK_AHEAD=5m, AHEAD_M=800/BEHIND_M=30
      （距離ウィンドウ外はdrawRangeで描画スキップ、パフォーマンス対策）
    カメラ左右位置: センターラインではなく左車線中心
      （左端からROAD_HALF_Wの半分＝LANE_OFFSET_M=4.0m＝道路全幅の25%）
      にオフセット。#updateCameraAt()内でperpAt()により進行方向の法線
      （+rx/+rz=左、-rx/-rz=右。three.jsの右手系Y-up規則での
      cross(forward, up)から導出。buildRibbonMesh等のsmoothedPerps()と
      同じ符号規則だが、そちらの near-left/near-right という変数名は
      実際の左右とは逆になっている点に注意）を求め、カメラ位置・lookAt
      注視点の両方を同じ量だけ左方向にシフトすることで視線の向きは
      センターラインと平行のまま視点だけ左車線中心にずれる

  からclient.connect()までの処理全体をtry/catchで囲む。以前はdb.get()
  がtry/catchの外にあり、ここで例外（Promise reject）が起きると
  client.connect()（navigator.bluetooth.requestDevice()を呼びネイティブ
  デバイス選択ポップアップを表示する処理）に到達せず、catchブロックも
  実行されないため、setStatus('connecting')のまま復帰不能になる不具合が
  あった（ポップアップも出ずBLEログにもエラーが出ないまま「接続中...」
  が固まる。走行中断からの復旧後に再接続できないという報告の実体は
  これで、複数タブでのBLE接続競合が原因ではなかった）。

  document.visibilitychange('hidden')でftms/cps/hrsの3クライアントを
  すべてdisconnect()する（spec.txt 3-6節・10-7-1節参照）。
  FtmsClient/CpsClient/HrsClientのdisconnect()は
  `if (this.#device?.gatt.connected) this.#device.gatt.disconnect()`
  という同期API呼び出しのみで、未接続時は何もしない安全なガード付き。
  狙いは、ホームボタン操作等でタブがバックグラウンドへ回った際に
  トレーナー等との接続を明示的に手放し、ブラウザの履歴／最近使った
  タブから別タブとして開き直された場合でも新しいタブから即座に
  再接続できるようにすること（BLEデバイスは通常1台のセントラルとしか
  同時接続できないため、元タブが接続を握ったままだと新タブの接続が
  「接続中...」のまま固まる／エラーになっていた）。beforeunload/
  pagehideと異なりvisibilitychangeはバックグラウンド化の瞬間に確実に
  発火し、disconnect()も非同期処理を待たない同期APIのため、実行漏れが
  起きにくい（10-7-1節のroute-session自動保存と同じ理由づけ）。
  フォアグラウンド復帰時の自動再接続は行わない（ユーザーが手動で
  「接続」ボタンを押す）。

10-7-1. main.js ライドセッション永続化・復旧（spec.txt 6-2-1節）
────────────────────────────────────────
  目的: beforeunloadはホームボタン操作・OSによるアプリ強制終了（taskkill
  等）ではモバイルブラウザ含め発火しないことが多く、これのみに頼った
  保存では走行データが失われる。定期タイマーによる自動保存を主たる
  防御線とし、beforeunload/pagehide/visibilitychangeは補助的に即時
  保存を試みるのみとする。

  永続化される2つの領域（ライフサイクルが異なる）:
    - チェックポイント（localStorage, キー'route-session'）:
      「再開」専用。単一スロットのため新しいライド開始で上書きされる。
      { routeId, routeName, startedAt, samples, simState,
        draftRideId } の形（draftRideIdはRideController.getCheckpoint()
        の返り値に自前で追加）。
    - 下書きレコード（IndexedDB rides ストア, isDraft:true）:
      履歴タブに常時表示され、チェックポイントが上書き・消失した後も
      「終了として確定・Stravaアップロード・削除」ができる
      （10-8節rideHistory.js参照）。

  main.jsモジュールトップレベル変数:
    draftRideId    走行中の下書きレコードID（未作成ならnull）
    autosaveTimerId 定期保存タイマーのID
    AUTOSAVE_INTERVAL_MS = 20000（20秒間隔）

  関数:
    checkpointToSummary(cp) → {routeId, routeName, startedAt(Date化),
      endedAt: new Date()（呼び出し時点を暫定終了時刻とする）, samples}
      下書き保存・終了モーダル表示の両方でチェックポイントから
      summary形状を組み立てる共通処理。
    saveRouteSession() → getCheckpoint()に{draftRideId}をマージして
      localStorageへ同期書き込み。
    autosaveDraft() → saveDraftRide(checkpointToSummary(cp), draftRideId)
      を呼び、返ったidをdraftRideIdへ書き戻す（初回はadd、以降はput）。
      samples.length<2の間は保存しない。
    autosaveTick() → saveRouteSession()とautosaveDraft()を両方呼ぶ。
      startBtn押下後・restoreFrom後にstartAutosaveTimer()で
      setInterval(autosaveTick, AUTOSAVE_INTERVAL_MS)を開始し、
      handleRideFinished内でstopAutosaveTimer()により停止する。
      pauseResumeBtnの一時停止時、beforeunload/pagehide/
      visibilitychange(hidden)でも即時にautosaveTick()を呼ぶ
      （IndexedDB書き込みは非同期のためpagehideでは完了を保証
      できないが、直近の定期保存が既にディスクへ同期済みのため実害は
      小さい。localStorageへの書き込みは同期的で必ず完了する）。

  handleRideFinished(summary):
    stopAutosaveTimer()を呼び、finishedDraftId = draftRideId を退避
    してdraftRideId = null にリセット。isDummyTrainer()がfalseなら
    rideEndModal.show(summary, {existingId: finishedDraftId})で
    下書きを確定記録に更新させる。isDummyTrainer()がtrueの場合は
    元々終了モーダルを出さず記録も保存しない仕様のため、
    finishedDraftIdが存在すればdeleteRide()で道連れに削除する
    （自動保存はisDummyTrainerを見ずに常時動くため、ここで破棄しないと
    ダミートレーナーのテスト走行が下書きのまま履歴に残り続けてしまう）。

  init()内の復旧フロー（旧: 無条件で即座にrestoreFromしていたものを
  ダイアログ選択式に変更）:
    routeSession = localStorage['route-session']をパースし存在すれば
    getRoute(routeSession.routeId)でルート実体を確認。
      - ルートが見つからない場合: draftRideIdがあればdeleteRide()、
        clearRouteSession()のみ行い、ダイアログは出さない。
      - 見つかった場合: showRideRecoveryDialog(routeSession, record)を
        awaitして、以下いずれかの選択をユーザーに委ねる。

    showRideRecoveryDialog(routeSession, record) → Promise
      #ride-recovery-overlay（index.html）を表示し、3ボタンに
      onclickを設定、選択後にcleanup()してresolve()するPromiseラッパー。
        [再開する] resumeRouteSession(routeSession, record)を呼ぶ
          （旧initブロックの中身をそのまま関数化したもの。draftRideIdを
          routeSession.draftRideIdから引き継ぎ、startAutosaveTimer()を
          呼ぶ点が新規）。
          【バグ修正】旧実装はeleView.setRoute(route)のみでmapView.
          setRoute(route)を呼んでいなかった（routePicker.jsのルート選択
          フロー経由でしか呼ばれない想定だったが、復旧フローはこの
          選択フローを経由しないため漏れていた）。この状態で
          restoreFrom()が即座にtick（10Hz）を開始しmapView.
          setCurrentPosition()が無条件にpanTo()するため、一度も
          fitBoundsされていない・タブがちょうど非表示から表示に
          切り替わった直後という不整合な状態でLeafletの内部タイル計算が
          破綻し、Uncaught Error: Attempted to load an infinite number of
          tilesがtickのたびに発生し続けていた（HUD更新等も巻き込まれて
          復旧後の画面全体が正しく動かないように見えた）。
          routePicker.jsの選択フローと同じくmapView.setRoute(route)を
          eleView.setRoute(route)の直前に追加して解消。

          【既知の制約・検証済み】Windows/Chromeでは、異常終了→復帰→
          「再開する」→トレーナー再接続→再走行まで一連の動作を確認済み。
          iOS(Bluefy)では、Bluefyアプリをバックグラウンドから復帰させた
          場合（アプリ自体は終了させていない）、Bluefy内部のWeb
          Bluetooth実装が古い接続状態を引きずり、トレーナーの「接続中...」
          から進まなくなることがある（別デバイスから同じトレーナーへは
          問題なく接続できるため、トレーナー側ではなくBluefy側の制約と
          切り分け済み）。Bluefyアプリを完全終了してから開き直せば解消
          する。アプリ側のコード（本節のBLE切断・自動保存等）では対処
          できない、Bluefyのブラウザ実装に起因する既知の制約として記録
          する（spec.txt 6-2-1節参照）。
        [ここまでの記録を終了して保存]
          checkpointToSummary(routeSession)でsummary化し、
          clearRouteSession()した上でrideEndModal.show(summary,
          {existingId: routeSession.draftRideId})。ダミートレーナー時は
          モーダルを出さずdeleteRide()のみ。
          （走行を再開させずにそのまま終了モーダルへ直行させることで、
          「もう一度アプリを開いて指でペダルを漕ぐ真似をする」ような
          再開操作なしに履歴・Strava保存まで到達できる）。
        [破棄]
          routeSession.draftRideIdがあればdeleteRide()、
          clearRouteSession()。

11. 実写風景写真（src/mapillary/）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  resample.js:
    resampleRoute(route, intervalM=20) — route.totalDistanceMを
      intervalM刻みで走査し、route.getPositionAt(d)で{lat,lon,
      distanceFromStartM}を生成する等間隔点列。GPXの生trkpt密度
      （直線区間ほどtrkptが疎になりがち）に依存させないため、Mapillary
      の先読み・シーケンス選定はこの出力のみを使う（3Dマップ・勾配計算
      等は従来通りroute.pointsを使用）。ルート選択時に1回だけ一括計算
      （数万点でも数ms・数MB程度でメモリ・速度とも問題にならないため、
      ライド中の逐次計算は行わない）。

  api.js:
    fetchCandidateImages(point) — {lat,lon}中心にGraph API `/images` を
      `lat`/`lng`/`radius`パラメータ（半径検索、SEARCH_RADIUS_M=35m、
      limit=100）でGET（fields: id, compass_angle,
      computed_compass_angle, geometry, computed_geometry, is_pano,
      sequence, quality_score, captured_at, thumb_1024_url, creator）。
      トークンはVITE_MAPILLARY_TOKEN。
      ※以前は`bbox`パラメータ（半幅35mの矩形）を使用していたが、実測で
      同一bbox・同一fieldsに対して同じリクエストを繰り返しても件数が
      毎回大きく異なる（例: 5回で1,0,0,0,7件）という重大な揺らぎを確認。
      `lat`/`lng`/`radius`方式に切り替えたところ、同一条件で5回とも
      完全に同じ結果（50件、gtatsu33件数13件で固定）となり、揺らぎが
      解消することを確認して採用（`bbox`と`lat`/`lng`/`radius`は
      Graph API仕様上併用不可）。`limit=100`を指定しても実際には50件
      までしか返らない（ドキュメント上のmax=100とは異なる実挙動）。
      ※シーケンスIDのフィールド名は`sequence`が正式名称（`sequence_id`
      は存在しない名前で、fields指定してもAPIに黙って無視され、常に
      undefinedになる。実データダンプで確認済みの既知バグを修正済み）。
    fetchThumbUrl(imageId) — サムネイルURLは長期キャッシュ不可のため、
      表示直前に単体エンティティを再取得して新鮮なURLを得る。

    precomputeBearings(points, window=2) — 各点に前後window点を使った
      大圏方位角(bearing)を付与。逆走時は反転済みpoint配列に対して
      呼ぶこと。resample.jsの出力に対して適用する。

  score.js:
    effectiveAngle(image) — computed_compass_angle優先、なければ
      compass_angle。
    effectiveGeometry(image) — computed_geometry優先、なければ
      geometry。GeoJSON Point([lon,lat])を{lat,lon}へ変換して返す
      （どちらも欠損時はnull）。
    isBehind(lastPos, candidatePos, bearingDeg)（非export）— lastPos→
      candidatePosのベクトルをbearingDeg方向へ平面近似で射影し、進行方向の
      負成分（後方）がBACKWARD_TOLERANCE_M=3mを超えるかを判定する。
    selectBest(images, point, activeSequenceId=null, haversineM,
      lastImagePosition=null) —
      pointは{lat,lon,bearing}。角度差>45°は除外(score=-1)。さらに、
      activeSequenceId継続中（image.sequence===activeSequenceId）かつ
      lastImagePositionが与えられている場合、そのシーケンス内で
      lastImagePositionより進行方向後方にある候補も除外(score=-1)する
      （シーケンス内の巻き戻り＝写真が逆走して見える現象の防止）。
      残った候補についてパノラマは`35 - diff×0.2 + quality×20 + recency`、
      通常写真は`50 - diff×0.3 + quality×20 + recency` を基礎スコアとし、
      distanceScore = max(0, 40 - 候補実座標までのhaversine距離[m])×0.5
      （0mで+20、40m以遠で+0、bbox半幅35mの対角付近で効かなくなる）と
      image.sequence===activeSequenceId時+20（SEQUENCE_BONUS、直前と
      同じ撮影シーケンスの継続を優先。15→20に強化）を加算。
      最高スコアの1件を返す（無ければnull）。

  cache.js:
    IndexedDB `mapillaryCache` ストア(KV)。CACHE_VERSION=11（sequence
      フィールド名修正・距離スコア・巻き戻り防止・bbox→radius方式への
      切り替えの導入に伴い更新、旧バージョンのキャッシュエントリは
      isStale()判定で自動的に再フェッチされる）。STALE_MS=90日。
    resolveImageForPoint(cachePrefix, idx, point, activeSequenceId,
      lastImagePosition) —
      戻り値は{image, reason}。キー `${cachePrefix}::${idx}`。
      有効キャッシュがあれば画像ありはサムネイルURLのみ再取得して返す
      （stripUrl）、画像なしはキャッシュ済みのreasonをそのまま返す
      （この場合、activeSequenceId・lastImagePositionによる再評価は
      行わない＝キャッシュヒット時は初回選定時の状態のまま）。
      無ければfetchCandidateImages+selectBest(candidates, point,
      activeSequenceId, haversineM, lastImagePosition)を実行し、reason=
      候補0件なら'no-candidates'、候補はあるが全REJECTなら
      'no-viable-candidate'、選定できたならnullとしてキャッシュへ保存。
      fetch自体の例外はここでは捕捉せず、呼び出し元
      （lookahead.js tick()）に伝播させる。

  lookahead.js:
    PRE_TRIGGER_M=8 — resample.jsの等間隔点列（既定20m間隔）に対し、
      間隔より十分小さいマージンを使うことで1tickでactiveIndexが
      2つ以上進まないようにする（旧実装は生trkpt向けの25m固定値
      だったが、20m間隔だと超過してしまうため縮小）。
    class ActiveIndexTracker(points) — update(currentDistanceM)で、
      次点のdistanceFromStartM-PRE_TRIGGER_Mを現在距離が超えたら単調に
      activeIndexを進める（ライド中の毎tickで使用）。
      seekTo(currentDistanceM) — 開始距離の選択・変更（複数日ライド）で
      任意距離へ前後どちらへも飛ぶための版。0から線形探索し直すため
      update()と違い逆方向の移動にも対応する。
    class MapillaryLookahead(cachePrefix, points, lookaheadPoints=12) —
      Map<index,{status,image,routeBearing,reason}>のバッファを持ち、
      tick(activeIndex)でactiveIndex+lookaheadPoints
      （既定12点×20m間隔で約240m先）まで1件ずつ先読み取得
      （#inFlightPromiseで同時1件に制限）。activeIndex-1より古い
      バッファは破棄。#activeSequenceId・#lastImagePositionを跨ぎ
      保持し、継続性ボーナス・巻き戻り防止の両方に利用
      （resolveImageForPointが返すimage.sequence /
      effectiveGeometry(image)で都度更新）。
      resolveImageForPointが例外を投げた場合（フェッチ失敗）は
      catchしてstatus='error', reason='fetch-error'として保存。
      getStateFor(index) → 未取得時は{status:'pending', image:null,
      routeBearing:null, reason:null}。resolveImageForPointの解決直後に
      panel.jsのpreloadImage(thumb_1024_url)を呼び、表示（activeIndex
      到達）より前にブラウザへ画像バイトを先読みさせる（切り替え時の
      黒画防止）。
      【2026-07-25修正】tick()呼び出し時に他のフェッチが#inFlightPromise
      として進行中の場合、以前はそのまま何もせずreturn（空振り）して
      いたが、これだと空振り直後に単発でgetStateFor()を見る呼び出し元
      （previewAtDistance()等）が永久にpendingのまま取り残される
      不具合があった（ライド終了直後にルート選択へ戻ると、直前の
      ライドtickの進行中フェッチと競合し、写真パネルがNo Imageのまま
      更新されないケースがあった）。修正後は、進行中フェッチがあれば
      `await this.#inFlightPromise` した上で `return this.tick(activeIndex)`
      と自分自身を再帰的に呼び直し、先行フェッチの完了を待ってから
      改めて次のフェッチを行う（黙って諦めない）。ライド中の高頻度
      呼び出し（10Hz）に対しても、単に手持ち無沙汰な待機が増えるだけで
      副作用は無い。
      seekTo(activeIndex) — 開始距離の変更でActiveIndexTracker.seekTo()と
      対にして呼ぶ。#nextFetchIndexをそのindexへ飛ばし、無関係になった
      #buffer・#activeSequenceId・#lastImagePositionをクリアする
      （そうしないと
      #nextFetchIndexが0から1件ずつ大きくジャンプ先まで追いつくのに
      非常に時間がかかる）。

  panel.js:
    preloadImage(url) — new Image()にurlを割り当てるだけの先読み
      ヘルパー。lookahead.jsのtick()から、画像が先読みバッファに
      入った時点（表示のおよそ300m/lookaheadPoints分前）で呼ばれる。
    REASON_MESSAGES — reason文字列から表示テキストへのマップ:
      'fetch-error' → "Failed to Load Photo"（API通信失敗）、
      'no-candidates' → "No Photos Nearby"（bbox内に候補が0件）、
      'no-viable-candidate' → "No Matching Angle"（候補はあるが
      全て角度差>45°でREJECT、または選定済みでも表示直前の25°
      再チェックで弾かれた場合の両方をこの1文言に統一）。
    updatePhotoPanel(status, image, routeBearing=null, distanceM=null,
      reason=null) — status==='pending'は無視（チラつき防止）。画像
      なしはREASON_MESSAGES[reason]を表示（未知reason時のfallbackは
      "No Photos Nearby"）。表示直前の再チェックとして
      DISPLAY_MAX_DIFF_DEG=25（キャッシュ選定時の45°より厳しい）を
      超えたら"No Matching Angle"にフォールバック。パノラマは
      transform-origin＋2倍ズームでrouteBearing方向を画面中央に
      クロップ。撮影者クレジット「© {username} / Mapillary」を表示。
    resetPhotoPanel() — プレースホルダー（"No Image"固定文言）に戻す。

  end-to-end フロー（main.jsのonRouteSelectedコールバック～
  rideController.js #tick、両者にまたがる）:
    ルート選択時: MAPILLARY_ENABLED（VITE_MAPILLARY_TOKEN有無）が
      trueなら precomputeBearings(resampleRoute(route)) を1回実行、
      cachePrefix = `${routeId}:${reversed?'r':'f'}` で
      MapillaryLookahead/ActiveIndexTrackerを構築（この時点ではまだ
      tickしない）。main.jsのpreviewAtDistance(selectedStartDistanceM)が
      tracker.seekTo(distM)→lookahead.seekTo(idx)→lookahead.tick(idx)の
      順で呼ばれ、開始距離（複数日ライドの再開地点、既定0）に対応する
      1枚目をプレビューする。同関数はルート選択直後（onRouteSelected）と
      開始距離の確定時（onStartDistanceCommitted、routePicker.js 10-7節）の
      両方から呼ばれる。

      【2026-07-25バグ修正】以前はonStartDistanceChanged（ドラッグ中の
      pointermove毎に連続発火）からもpreviewAtDistanceのフル処理（写真
      取得込み）を呼んでいたため、以下の不具合があった:
        MapillaryLookahead.tick()は#inFlightで同時1フェッチに制限して
        いるため、ドラッグ中に発生する大量の呼び出しのうち実際に
        フェッチが走るのは最初の1回だけで、以降の呼び出しは
        lookahead.seekTo()でバッファ・#nextFetchIndexをリセットする
        だけの空振りに終わる。最初のフェッチがネットワーク遅延で
        一番最後に解決するため、ドラッグ終了（release）時点の位置では
        なく、ドラッグを開始した最初の位置の写真が最後に上書き表示
        されてしまっていた。
      修正: onStartDistanceChangedはpreviewAtDistance(distanceM,
      {withPhoto:false})に変更し、3D/2Dマップ・標高プロファイルの
      ライブ更新のみ行う（Mapillary処理を呼ばない）。写真取得を伴う
      フル同期は、値確定時のみ1回発火するonStartDistanceCommitted
      （ドラッグのpointerup／入力欄のchange）からのみ呼ぶことで、
      非同期処理の競合自体を発生させないようにした。
    ライド中: rideController.js #tick 内で
      tracker.update(distanceM)→activeIdx、
      lookahead.tick(activeIdx)（非同期）、
      lookahead.getStateFor(activeIdx)（reason含む）を updatePhotoPanel
      に渡す。

    ライド終了時（handleRideFinished）: previewAtDistance(lastDistanceM)
      をフル同期で1回呼ぶ（10-1e節）。【2026-07-25バグ修正】ライドの
      最後のtickによる進行中フェッチとここでの呼び出しが競合すると
      （lookahead.js 11-2節参照）、以前は空振りしたまま誰も再試行せず
      写真パネルがNo Imageで固まる不具合があった。lookahead.js側の
      tick()を「進行中フェッチを待って自分自身を再試行する」実装に
      直したことで解消（呼び出し側であるここの変更は無し）。

      【2026-07-25バグ修正・その2】上記とは別に、previewAtDistance()が
      当初init()内のローカル関数として定義されていたため、モジュール
      トップレベルの関数であるhandleRideFinished()から呼ぶと

      previewAtDistance()が参照するmapView/eleView/

      モジュールトップレベルのlet変数のため、関数自体をモジュール

12. FIT生成（src/export/fitWriter.js）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

外部FITライブラリを使わず、バイナリを直接組み立てる自前実装。

  FIT_EPOCH_MS = Date.UTC(1989,11,31)
  グローバルメッセージ番号: FILE_ID=0, ACTIVITY=34, SESSION=18,
    LAP=19, RECORD=20
  ベース型: ENUM=0x00, UINT8=0x02, UINT16=0x84, SINT32=0x85,
    UINT32=0x86

  class ByteWriter（非export）— u8/u16/u32/s32のリトルエンディアン
    書き込みヘルパー、.bytesでUint8Array取得
  fitCrc(bytes) — FIT標準のCRC-16（nibbleテーブル方式）
  writeDef(w, localType, globalNum, fields) — FIT定義メッセージ書き込み
  fitTs(ms) → FITタイムスタンプ（FIT epoch起点の秒）
  semicircles(deg) → round(deg × 2^31/180)（緯度経度のFIT表現）
  altRaw(m) → round((m+500)×5)、[0,0xFFFE]でクランプ、null時0xFFFF(invalid)
  avg(arr, fn) → fn(x)>0の要素のみで平均

  buildFit(summary) → Uint8Array（GPS付きルートライド用）
    summary: {routeName, startedAt, endedAt, samples:[{timestampMs,
      lat, lon, elevationM, distanceM, velocityMs, powerW, cadenceRpm,
      heartRateBpm}]}
    メッセージ順: FileID → Record(サンプル毎、緯度経度はsemicircles、
      標高はaltRaw、距離は×100、速度は×1000) → Lap
      （event=9/event_type=1固定値、total_elapsed_timeはミリ秒を
      そのままuint32格納 = FIT仕様上のスケール1000秒フィールドと
      解釈上整合） → Session（sport=2/サイクリング,
      sub_sport=58/バーチャル活動、平均値、total_ascent=calcAscent()）
      → Activity（event=26/event_type=1）
    ヘッダー14バイト + データ + データ部CRC(2バイトLE) で構成
    （buildHeader()）。routeNameは文字列としては書き込まれない
    （呼び出し元がStravaアップロード時の名前として別途使用）。

  buildWorkoutFit(summary) → Uint8Array（GPS無し、ワークアウト用。
    Stravaへtrainer=1でアップロードする想定）
    summary: {workoutName, startedAt, endedAt, samples:[{timestampMs,
      powerW, cadenceRpm, heartRateBpm, distanceM?, velocityMs?}]}
    Recordから緯度経度・標高を除外、Session.sub_sport=6
    （インドアサイクリング）、total_ascentフィールドなし。それ以外は
    buildFit()と同じメッセージ構成。

  buildHeader(dataSize) — サイズ14, protocol=0x20, profile version=2132,
    データサイズ(u32 LE), ".FIT"マジック, 先頭12バイトのCRC(u16 LE)
  calcAscent(samples) — 連続サンプル間の正の標高差の合計

13. Strava連携の実装
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

13-1. src/strava/auth.js（クライアント側）
────────────────────────────────────────
  startAuthorization() — `https://www.strava.com/oauth/authorize` へ
    window.location.href でリダイレクト。パラメータ:
    client_id, redirect_uri, response_type=code,
    scope='activity:write,read', approval_prompt=auto。
    PKCE不使用（クライアントシークレットはサーバー側関数に隠蔽する
    標準の認可コードフロー）。

  exchangeCode(code) → tokens
    同一オリジンの `/strava-exchange`（Cloudflare Workers、
    src/worker/index.js）へ{code}をPOST。レスポンスから
    {accessToken, refreshToken, expiresAt(unix秒), athleteId,
    athleteName} を組み立て、settings.stravaTokensへ保存。

  refreshAccessToken(tokens)（内部関数、非export） → accessToken
    `/strava-refresh` へ{refresh_token}をPOSTし、access_token/expires_at
    のみ更新して保存する。失敗時（応答が非OK、通信エラー等）は
    disconnect()を呼びsettings.stravaTokensを削除したうえで例外を
    再throwする
    （※ Stravaがrefresh_tokenをローテーションした場合、レスポンスの
    新refresh_tokenを保存していない実装になっている点に注意
    ―将来的な改善候補）。

  getValidAccessToken() → accessToken
    expiresAt > now+60秒 ならキャッシュ済みトークンをそのまま返す
    （Stravaへの問い合わせなし）。それ以外はrefreshAccessToken()を
    呼び出す。リフレッシュ失敗時はrefreshAccessToken()内でdisconnect()
    済みの状態で例外が伝播する（呼び出し元のuploadToStrava()等で
    catchされても、DB上の接続状態は正しく「未接続」になっている）。

  getConnectionInfo() → {athleteName, athleteId}|null
    stravaTokensの存在有無のみを見る（有効性検証は行わない）。

  disconnect() → settings.stravaTokens削除

  verifyConnection() → boolean
    起動時（main.js init()）およびSettingsタブ表示のたび
    （updateStravaStatusUI()内）に呼び出す接続検証関数。
    stravaTokens未保存なら即falseを返す。保存済みならexpiresAtに
    関わらず必ずrefreshAccessToken()で実際にStravaへ問い合わせ、
    成功すればtrue。失敗（refresh_token失効等）時はrefreshAccessToken()
    内でdisconnect()が呼ばれた状態でfalseを返す。
    getValidAccessToken()と異なりキャッシュを信用しないため、
    Strava側で連携解除された場合など「ローカルのexpiresAtはまだ有効
    だが実際には無効」なケースもここで検知できる。

13-3. src/strava/upload.js
────────────────────────────────────────

13-5. Street View中継（src/worker/index.js, ui/googleMapView.js）
────────────────────────────────────────
  オーナーモードでGoogle Maps代替を使用時、googleMapView.js は

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    fetch:
      - ナビゲーションリクエスト（event.request.mode === 'navigate'、
        HTML本体）: ネットワーク優先。失敗時（オフライン）のみ
        キャッシュ、それも無ければ '/' のキャッシュにフォールバック
      - それ以外（ハッシュ付きJS/CSS・アイコン等）: cache-first
        （ファイル名にコンテンツハッシュを含むため、キャッシュ優先で
        問題ない）

  登録: index.html末尾のインラインscriptで
    `navigator.serviceWorker.register('/sw.js')`（main.jsではなく
    index.html側に直接記述されている点に注意）。

  __APP_VERSION__: vite.config.local.js / vite.config.js で
    package.jsonのversionを読み込みビルド時定数として注入。
    main.jsが `#app-version` 要素に 'v' + __APP_VERSION__ を表示。
    オーナーモード時は隣接する `#owner-badge` に "(o)" が表示される
    （詳細は13-4節）。

15. Cloudflare Workers デプロイ設定
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  現状（2026-07-11時点）: GitHub連携（Workers Builds）設定済み。
  `main`ブランチへのpushで自動ビルド・デプロイされる
  （ビルドコマンド: npm run build、デプロイコマンド: npx wrangler deploy）。
  Cloudflareダッシュボードの「Settings → Build」にビルド時変数
  （VITE_*、7変数）、「Settings → Variables & Secrets」に実行時
  シークレット（4変数）を設定済み。

  手動デプロイ（15-2〜15-4）は、ローカルでの動作検証や、Workers Builds
  側の自動デプロイが失敗した際の復旧手段として残す。通常の変更反映は
  git push のみで完結する。

  ⚠ 15-3[1]で判明した「`wrangler secret put`だけではシークレットが
  反映されないことがある」問題が、Workers Builds のデフォルトデプロイ
  コマンド（`npx wrangler deploy`、--secrets-fileなし）でも起こり得るか
  は未検証。自動デプロイ後は `GET /api/auth?owner=xxx` 等で実行時
  シークレットが正しく効いているか確認すること。もし同じ問題が
  再発する場合は、Cloudflareダッシュボードの「Variables & Secrets」
  パネルでの設定（プラットフォームネイティブの経路）が正しく機能して
  いるかを疑うこと。

────────────────────────────────────────
15-1. wrangler.jsonc
────────────────────────────────────────
  {
    "name": "gpx-vcycl",
    "compatibility_date": "2026-07-11",
    "main": "./src/worker/index.js",
    "assets": {
      "run_worker_first": ["/strava-exchange", "/strava-refresh", "/api/*"]
    }
  }

  `assets.directory` は指定しない（@cloudflare/vite-plugin がビルド時に
  自動決定するため、手動指定すると衝突する）。Worker名（"name"）は
  Cloudflareダッシュボード上のWorker名と一致している必要がある。

────────────────────────────────────────
15-2. 初回セットアップ手順
────────────────────────────────────────
  1. npx wrangler login              （ブラウザでCloudflareアカウント認証）
  2. .dev.vars を作成し、4章のサーバー側専用4変数を記入
     （.dev.vars.example をコピーして使う。git管理外）
  3. npm run build                    （dist/ を生成。VITE_変数が
                                        ビルド時に焼き込まれる）
  4. npx wrangler deploy --secrets-file .dev.vars
     （コードと実行時シークレットを同時にアップロードする。後述15-3参照、
     単独の `wrangler secret put` より確実）

────────────────────────────────────────
15-3. 既知の落とし穴（実装時に実際に発生した問題）
────────────────────────────────────────
  [1] `wrangler secret put <NAME>` を個別に実行しただけでは、後続の
      `npm run deploy`（vite build && wrangler deploy）でシークレットが
      Worker実行時に反映されないことがあった（@cloudflare/vite-plugin が
      生成する「リダイレクトされたwrangler設定」経由のデプロイ特有の
      挙動と推測される。原因は完全には特定できていない）。
      → 対策: `wrangler deploy --secrets-file .dev.vars` で、コード
        デプロイと同じタイミングでシークレットを明示的に添付する。
        このフラグは「ファイルに含まれないシークレットは前バージョンから
        保持される」ため、繰り返し実行しても安全（追記のみ・非破壊的）。

  [2] `.dev.vars` で新規Workerに初めてシークレットを設定しようとすると、
      「Worker "gpx-vcycl" が存在しません。作成しますか？」という
      確認が出る（非対話実行時は自動でyes扱いになる）。これは想定通り
      の動作で、空のWorkerが作成された後、実コードのデプロイで
      上書きされる。

  [3] VITE_STRAVA_REDIRECT_URI のようなビルド時変数は、ローカル開発
      （LAN IP）と本番（Workersの公開URL）で値が異なる。.env に開発用の
      値を書いたままにすると、本番ビルドにも開発用URLが焼き込まれ、
      Strava認可画面で `{"errors":[{"field":"client_id","code":"invalid"}]}`
      のようなエラーになる（client_idそのものは正しくても、
      redirect_uriやビルドタイミングの環境変数未定義が原因で
      client_idが `undefined` 文字列として送信されてしまうケースが
      あった）。
      → 対策: `.env.production` を作成し、本番URLを使う変数
        （VITE_STRAVA_REDIRECT_URI 等）だけをそこに上書き定義する。
        `vite build` はデフォルトで production モードのため
        `.env` → `.env.production` → `.env.local` の順で読み込み・
        マージされる。デプロイ前に、生成されたバンドル内に
        期待する値が実際に含まれているか確認すること
        （例: `curl <デプロイURL>/assets/index-*.js | grep <期待する値>`）。

────────────────────────────────────────
15-4. 通常の反映方法（Workers Builds経由）
────────────────────────────────────────
  main ブランチへ git push するだけでよい。Workers Builds が
  自動的に npm run build → npx wrangler deploy を実行する。
  デプロイ完了後は動作確認すること（例: GET /api/auth?owner=xxx が
  200を返すか）。

  ローカルから手動で反映したい場合（緊急復旧・検証用途）:
    npm run deploy
      package.json: "deploy": "vite build && wrangler deploy"
      ※ シークレットに変更がない場合はこれで十分だが、15-3[1]の問題が
        再発する可能性があるため、デプロイ後は必ず動作確認すること。
        シークレットを変更した場合は15-2の手順4
        （--secrets-file 付き）を使うこと。

────────────────────────────────────────
15-5. 環境変数のまとめ（再掲）
────────────────────────────────────────
  ビルド時（VITE_*、7変数）: .env / .env.production / .env.local
